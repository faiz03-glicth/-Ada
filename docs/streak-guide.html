Streak, and how it's built

A habit app where every check-in darkens today's square on a heatmap. This guide explains the code as it stands: what's finished, how the pieces talk to each other, where the data goes, and what to check first when something breaks.

02 · The stack

One job per technology

Several libraries sound like they overlap. This list says which one is actually responsible for each job.

App runtime
Expo SDK 57 · React Native 0.86 · React 19 · TypeScript (strict)Runs in a development build, not Expo Go, because it uses native modules like audio and Google Sign-In.
Screens & navigation
Expo Router with typed routesEvery file in app/ is a screen. Two groups, (auth) and (app), are switched by guards, not by navigation calls.
The truth (on phone)
SQLite (expo-sqlite) through Drizzle ORMThe app reads from here first. It works offline and it's the only store guests have.
Backend
Supabase: Auth + Postgres behind row-level securityThere's no server code of your own. The app calls Supabase directly with supabase-js.
Server data in memory
TanStack QueryHolds fetched data for 30 seconds, retries only network failures, and refetches when you reopen the app. Nothing is saved to disk.
App state
Zustand, saved to a synchronous SQLite key/value storeSign-in status, onboarding progress, theme and sound choices. Because it loads synchronously, the first frame already knows where to go.
Styling
Unistyles 3, built from design tokensLight, dark, the "glass" look and 4 heat palettes, all from one theme builder.
Motion
Reanimated 4 + WorkletsEvery animation runs on the UI thread and takes its timing from one tokens file.
Feedback
expo-haptics · expo-audio · sonner-native toastsThe sounds are generated from the same numbers as the animations.
Validation
zodChecks env values at launch, email input, and every row Supabase sends back.
Quality & builds
Jest + Testing Library · Maestro · ESLint · Prettier · GitLab CI · EAS Buildnpm with Node 24. CI fails on any lint warning.

Installed but never imported by app code: date-fns, expo-blur, expo-glass-effect. No analytics, crash reporting or over-the-air updates yet.

04 · Launch

What happens between tapping the icon and the first screen

The splash stays up until the app knows exactly where to send you, so it never flashes the wrong screen.

  1. Theme is ready before anything drawsSaved theme choices load synchronously and Unistyles is configured (index.ts → theme/unistyles.ts).
  2. Three checks run in parallel, splash heldEnv values valid? Fonts loaded? Local database migrated? The first failure shows a readable error screen instead of the app (BootGate).
  3. Repositories are created onceThe Supabase client and Google Sign-In are set up only now, so a bad .env can't crash the app at import (RepositoriesProvider).
  4. The session is restoredSigned in, guest, or signed out? See the decision below (SessionGate → restoreSession).
  5. Splash hides, guards pick the screenIn a session and onboarded → the app. Otherwise → onboarding or login.

Session restore: how the app decides who you are

Supabase has a valid session (it may refresh the token first)Signed in
Offline and the token expired → use the last signed-in user's local profileSigned in, offline
No session, but guest_id exists and guest_active = 1Guest
None of the above, or an unexpected errorSigned out
05 · Signing in

Four ways in, one shared ending

There are no passwords anywhere. Whichever provider you use, a successful sign-in ends with the same steps, and the route guard moves you on without any navigation call.

  1. Make a random nonce32 random bytes. Apple gets its SHA-256; Supabase gets the raw value to check the token against.
  2. Native Apple sheetiOS only. The button is hidden where Apple sign-in isn't available.
  3. Supabase signs in with the ID tokensignInWithIdToken('apple', token, nonce)
  4. Save the name straight awayApple sends your name only on the very first sign-in, so it's written to Supabase and the local profile immediately. Failures here never block sign-in.
  1. Check Play servicesAndroid only.
  2. Native Google pickerCancelling is silent: no error banner.
  3. Supabase signs in with the ID tokenNo nonce. Supabase's "Skip nonce check" must be on. On Android the signing key's SHA-1 must be registered in Google Cloud.
  1. Validate the addressTrimmed and lower-cased, then checked with zod. "Send code" stays disabled until it's valid.
  2. Supabase emails a 6-digit codeThe account is created on first use. A resend cooldown starts.
  3. Sixth digit submits automaticallyA wrong or expired code shows a message under the field, not a banner.
  1. No network at all"Skip" on the login screen, or finishing onboarding while signed out.
  2. Reuse or create a guest idStored in app_meta as guest_id, with guest_active = 1.
  3. A local-only profile rowprovider = 'guest', user_id = NULL. Logging out keeps the data so the guest can resume.

The shared ending (completeSignIn)

  1. Save the profile locallyAn upsert that never erases a name or photo the provider didn't send this time.
  2. Hand over guest dataIf a guest was using the phone, their rows move to the new account in one transaction and the guest profile is retired.
  3. Remember who signed inlast_user_id is saved so the app can restore you offline.
  4. Update the storeStatus becomes signed in. The guard sends a new account to onboarding and a returning one to Home with a "Signed in with …" toast.

Logging out

A native confirm, then: a guest only clears guest_active, and a member signs out of Google, then Supabase (this device only), then forgets last_user_id. On success the query cache is cleared and the guard shows Login. Offline, logout fails with "You're offline".

06 · Where data lives

Four stores, and why each one exists

This is the caching setup. Each store has one job, so nothing is saved in two places.

DB

SQLite database · streak.db

The source of truth. Profiles and device bookkeeping. The screen reads here first, so it's instant and works offline.

Lasts until the app is deletedCode core/db, data/local
Q

TanStack Query cache

In-memory copy of what the screen shows. Fresh for 30 seconds. Refetches when you reopen the app or come back online. Sign-in marks the profile stale; sign-out wipes it.

Lasts until the app closesCode core/query, useProfile.ts
KV

Preferences key/value store

Zustand stores saved to expo-sqlite/kv-store: onboarding progress, theme, reduce motion, sound. Read synchronously, so the first frame is already right.

Keys streak.auth · streak.theme-preferences · streak.sound-preferences
🔒

Encrypted session

Supabase's login tokens. A fresh AES key goes in the phone's secure keystore; the encrypted session goes in AsyncStorage (the keystore can only hold about 2 KB). Tokens refresh only while the app is open.

Code core/supabase/LargeSecureStore.ts

How a profile reaches the screen

  1. Read SQLiteShown immediately, even offline.
  2. If online and not a guest, fetch from SupabaseThe response is checked with zod before use.
  3. Unless the local row has unsaved editsA dirty row wins and the server copy is ignored.
  4. Write SQLite, update the cacheThe screen re-renders with the fresh data.
07 · Database

Two tables on the phone, one on the server

profiles · phone

One row per person. id is the Supabase user id, or a random id for a guest. Carries the sync columns every future table will have: user_id, created_at, updated_at, deleted_at (soft delete) and dirty (unsaved edits).

app_meta · phone

Device bookkeeping, never synced: guest_id, guest_active, last_user_id, and last_pulled_at (reserved for the Phase 5 sync).

public.profiles · Supabase

Created automatically by a trigger when someone signs up. Each person can read, create and update only their own row. There's no delete permission; account deletion is planned for a server function.

There are no indexes beyond primary keys and no foreign keys on the phone yet. That's fine for two tiny tables, but it needs attention when check-ins arrive.

Where the phone and server disagree

These differences will cause errors once the sync engine exists.

Column Phone Server
provider also allows guest apple · google · email
time_zone required optional
username not unique unique
user_id, dirty present absent
timestamps text timestamptz

The one transaction

When a guest signs in, reassignGuestData gives the guest profile the new user id, marks it deleted, and removes the guest keys, all or nothing. When activities and check-ins are added, they must be moved in this same transaction.

08 · Bugs

Nothing critical, four worth fixing soon

Found by reading the code; none were reproduced on a device. Open one to see the cause and the fix.

Medium B1Offline profile edits are never retried
What you'd see
A name change made offline never reaches the server, and later server changes never reach the phone.
Cause
A failed push leaves the row marked dirty. Nothing re-pushes it until the Phase 5 sync engine, and dirty rows block server updates.
Fix
Push dirty rows on reconnect or when the app opens.
Files
LocalFirstProfileRepository.ts
Medium P1You can't log out while offline
What you'd see
"You're offline" and you stay signed in, but Google's account choice has already been cleared.
Cause
Google sign-out runs before Supabase sign-out, and a network failure is treated as a failed logout.
Fix
Clear the local session anyway, or sign out of Google only after Supabase succeeds.
Files
SupabaseAuthRepository.ts, shared/actions/session.ts
Medium P2A database failure at startup would crash, not show the error screen
Cause
The database is opened when the file is imported, before the boot error screen exists.
Fix
Open it inside the migrations boot task, or wrap it in a try.
Files
core/db/client.ts
Medium B4Onboarding picks aren't saved as real data
Cause
The chosen activities and reminder setting live only in the saved onboarding draft. No activities table exists yet.
Fix
Phase 2 creates activity rows from the draft when onboarding finishes.
Suspected S1Session can be lost if the app dies mid-save
Cause
The new key is written before the encrypted session. If the app is killed between the two, the next read decrypts garbage and you're signed out.
Fix
Version the key or add an integrity check, and treat a failed decrypt as "no session".

09 · Performance

What's already fast, and what to do before Phase 2 gets heavy

Implemented
  • No wrong-screen flashSynchronous saved state and a held splash.
  • Parallel boot checksEnv, fonts and migrations at once.
  • Smooth motionUI-thread animation, transform and opacity only, memoised pages and heatmap cells.
  • Cheap theme changeOne fading veil; nothing re-renders per frame.
  • Quiet networkRetry only network failures, refetch on reopen, never poll. Guests never hit the network.
  • BatteryToken refresh only while the app is open.
  • Smaller app5 font weights, smaller icons, arm64-only preview APK with R8 shrinking.
  • Sounds on cuePlayers preloaded and kept.
Recommended
  • Indexes for check-inse.g. on (user_id, date), added with the table.
  • Count days in SQLQueries run on the JS thread; aggregate with GROUP BY and fetch only the visible range.
  • Use or drop the change listenerIt's on, but no live queries use it.
  • One key/value engineMove the session off AsyncStorage onto the SQLite store.
  • Compress sounds~336 KB of WAV could be AAC.
  • Longer remote profile freshness5–10 minutes instead of 30 seconds.
  • Crash reportingThree TODO(Sentry) spots are waiting.
10 · Rules not to break

Things that look odd but are deliberate

Don't navigate after sign-in or sign-out

Change the store; the route guards move people. A router.replace would race with them.

Only shared/actions touches the router

Paths are written in routes.ts only. ESLint blocks the rest.

No styles in app/

The Unistyles Babel plugin only processes src/.

No raw animation numbers

Use the motion tokens and presets. A raw duration ignores Reduce Motion.

Never set tab animation to "none"

It remounts every tab on iOS (the blank-tabs bug).

Change motion tokens → rebuild sounds

A test compares sound-timings.json with the tokens.

Don't edit applied migrations

Change the schema and run npm run db:generate for a new one.

Don't persist the query cache

SQLite already holds the data; two copies would disagree.

Merge on GitLab only

GitHub is a mirror; merges there get overwritten.
